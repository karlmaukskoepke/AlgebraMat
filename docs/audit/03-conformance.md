## C. Progress loss after site updates: likely causes

Ranked by how likely each is to explain "progress sometimes disappears after an update". None of this has been fixed.

1. **Signing in does not survive a reload (observed, high).** `syncStore.loadSync` keeps the saved sign-in only if it has a `period` and a `number` (`src/syncStore.js:15`). Google sign-in saves `{ mode: 'device', id, token }` (`src/sync.js:28`), which has neither, so **every page load signs a Google-signed-in student out without saying so**. An update forces a reload, so after every update the sheet stops receiving progress and can't give it back. The file hasn't changed since 2026-10-04, before Google sign-in was added. No test covers it. *Quick check for Karl:* sign in, reload the page; if the button says "Sign in" again, this is it.
2. **An older tab overwrites newer progress (observed, high).** The app reads saved progress once, at load (`main.js:100-101`), and every save writes its in-memory copy over what is stored (`main.js:118`), without merging. So a second tab, or a tab left open from before an update, writes back an older picture. Worse, an **old bundle drops cards it doesn't know**: `normalizeProgress` keeps only the packs in its own list (`progress.js:75-77`), so a tab opened before Divide it shipped erases Divide it progress the next time it saves (going home saves). The safety-net copy is written (`main.js:116`) but **nothing ever reads it back**. On Chromebooks, tabs stay open for days, so this fits "after site updates".
3. **The browser or device clears storage (inferred, medium).** District-managed Chromebooks can be set to clear site data at sign-out; an iPhone home-screen install has storage separate from Safari; Safari may clear storage of a site not opened for 7 days (`navigator.storage.persist()` is asked, `main.js:107`, but may be refused). I can't see the district's settings (04, Q4).
4. **A save code doesn't carry opened levels (observed, medium).** Codes hold finished levels only. Levels the diagnostic opened (`open`) are lost when a student restores from a code, so they see levels locked again (`encodeProgress`, `progress.js:289`).
5. **Future level-count changes shift bits (observed mechanism, low today).** Progress is stored by level position. Combine it and Boxes needed hand-written realignments (`progress.js:81-87`); any card whose levels change without one would scramble. Today's counts are consistent with the v14 layout.
6. **A resumed level shows different problems (observed, low).** After an update, the level in play is regenerated from its seed with the new generator, so the same index can be a different problem. Finished levels are unaffected.
7. **Moving the site to a new address (observed comment, future).** `ci-deploy.yml` notes the base will change to a grafables.com path. A new domain is a new storage origin: every student would start empty unless they use a save code or the sheet (which needs cause 1 fixed).
